Until July 19, connecting a local OpenAdapt runtime to OpenAdapt Cloud meant opening the dashboard, copying a long-lived token, and pasting it into `login --token`. That path still works. [PR #1023](https://github.com/OpenAdaptAI/OpenAdapt/pull/1023) in the launcher adds a second one: `openadapt connect`.

The command itself does almost nothing. It delegates a fixed set of arguments, pairing ID, desktop URI, host, device, destination, to the Flow CLI, and pins the launcher's install route to `openadapt-flow>=1.17.0,<2` so the resolved engine actually contains the pairing state machine described below. The launcher also now installs the keyring-backed hosted extra as part of the base package, checks that the interpreter is in Flow's supported 3.10–3.12 range before dependency resolution even starts, and rejects a release wheel or sdist whose `Requires-Python` metadata drifts from `pyproject.toml`. None of that is glamorous. All of it exists because a clean install with the wrong engine version would make the rest of this story false.

The actual state machine lives in Flow, added by [openadapt-flow #151](https://github.com/OpenAdaptAI/openadapt-flow/pull/151). It parses only the narrow `openadapt://connect` contract, nothing looser. Before it touches any credential, it checks for a real OS keychain and refuses the pairing outright if one isn't available. If the check passes, it snapshots the prior canonical credential (so there is something to restore) and writes the newly issued credential to a pairing-specific private staging record, separate from canonical storage. The staged token gets validated from memory before it is ever promoted.

Promotion itself waits on Cloud. Flow confirms the exact pairing idempotently, retrying on response loss or a 5xx with the same token and the same pairing rather than minting a new attempt. If Cloud gives a definitive failure before confirmation, Flow calls Cloud's exact-token authenticated abort endpoint, and only restores or deletes canonical state after that abort call returns 200 with `revoked: true`. If the confirm or abort response is itself ambiguous, or restoration fails, Flow leaves both the new canonical state and the staging record in place rather than guessing. Success is reported only after Cloud confirms the keychain-backed connection.

That last branch is the one we think matters most. The obvious failure mode for any credential handoff is the moment when the network goes quiet right after the new credential is issued but before either side is sure the other saw it. Delete the old credential too early and a legitimate session breaks with no record of why. Trust an unconfirmed new credential and you've silently downgraded the account's security posture. PR #151 handles both by refusing to resolve the ambiguity locally: it holds both credentials, staged and canonical, until a subsequent confirm or abort gives a definitive answer.

The Desktop side, [openadapt-desktop #23](https://github.com/OpenAdaptAI/openadapt-desktop/pull/23), is where the URI actually enters the system. Desktop registers for the `openadapt` protocol across its supported Tauri installer targets and forwards links from a second app instance through the deep-link event rather than opening a new window. It accepts exactly one action, `openadapt://connect`, and hands that URI to one fixed in-process pairing command. There's no shell escape, no navigation escape, no way to point the handler at an arbitrary host. Malformed input, duplicate input, unknown actions, multiple URLs in one call, argument-shaped payloads, non-managed or non-loopback-local hosts: all of it gets refused twice, once in the Rust shell and again in the Python engine underneath it. If a secure keychain isn't available, pairing refuses before it ever consumes the one-use secret. The credential itself is never written to config, logs, events, subprocess argv, or a return payload at any point in the flow. Verification for this PR reports 5 passed Rust tests, 51 passed Python tests, a clean `ruff check`, and a passing `npm run build`; we're citing those from the PR body and haven't rerun them ourselves.

Nothing here removes the old paths. Manual `login --token`, the environment-variable route, and the explicit plaintext fallback all still exist in Flow after #151, and the launcher's README was updated rather than rewritten to describe `openadapt connect` as an addition. If you're scripting a headless install where no interactive protocol handler exists, you still reach for a token. What changed is that the interactive path no longer requires anyone to see, copy, or store one.

We'd argue the interesting design decision isn't the CLI at all, it's that the CLI is thin on purpose. `openadapt connect` doesn't implement pairing logic; it validates versions and calls into Flow's state machine, which is the piece actually carrying the safety properties, staged storage, idempotent confirm, definitive-only promotion. A thinner command surface with a heavier, independently tested core seems like the right split for something that handles credentials, and we'd expect an onboarding flow that put this logic directly in installer scripts to be harder to audit, even if it shipped faster.
