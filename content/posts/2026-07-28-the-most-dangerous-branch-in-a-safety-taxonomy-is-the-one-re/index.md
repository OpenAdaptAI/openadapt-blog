Here is a for-loop that returns `False` on every input, including the one input where `False` means something serious.

`_has_unresolved_uncertainty()` in Flow's runtime walks `result.effect_evidence` looking for anything unresolved. If it finds nothing, it returns `False`. That's correct behavior when the list has entries and none of them are uncertain. It's also exactly what happens when the list is empty because verification never ran at all. The loop body doesn't execute. There's nothing to iterate. `False` comes back either way, and the caller can't tell which case it's looking at.

That distinction sounds academic until you see what read the return value. [PR #280](https://github.com/OpenAdaptAI/openadapt-flow/pull/280), merged July 27th and labeled a P0 soundness defect, describes what `classify_transaction_outcome()` did with it: whenever the coarse outcome was `HALTED`, no policy rejection applied, and `_has_unresolved_uncertainty(report)` came back `False`, the function fell through to `TransactionOutcome.HALTED_BEFORE_EFFECT`. The inline comment on that branch claimed this represented "a governed halt with the verifier having established no effect." Nothing on that path had established anything. It had just failed to find uncertainty in a list that was never populated.

To see why that matters, you need the taxonomy it's classifying into. [PR #259](https://github.com/OpenAdaptAI/openadapt-flow/pull/259) replaced Flow's old success/halt/failure model with explicit terminal transaction outcomes, among them `VERIFIED`, `HALTED_BEFORE_EFFECT`, `RECONCILIATION_REQUIRED`, `FAILED_PLATFORM`, `CANCELED`, and `REJECTED_POLICY`. Each name is a claim about what's known, not just what happened. `HALTED_BEFORE_EFFECT` is documented, per #280, to mean the verifier established that no effect occurred. A customer who receives that outcome reconciles nothing. There's no unaccounted write to chase down, no downstream record to check, because the system told them there's nothing there.

Except the branch that produced it never established that. It produced it whenever a run halted early enough that the effect verifier had nothing to work with. Aborting before verification runs and having verification run and clear are two different events, and the code treated them as the same event because both leave `effect_evidence` empty. Absence of evidence became evidence of absence, in the one place a safety system can least afford that substitution: the terminal state a customer is told means stop looking.

Play out the failure the PR's own language points at. A run halts partway through a workflow. Maybe the halt happened after an action landed, before its effect could be checked. The classifier sees `HALTED`, sees no policy rejection, sees an empty evidence list, and returns `HALTED_BEFORE_EFFECT`. The customer reads that as "nothing landed, reconcile nothing," files it, moves on. If a write actually went through, it now sits in their system of record, unflagged, undetected, indistinguishable from any other row. That's the silent-wrong-effect failure this entire product exists to catch, arriving through the taxonomy meant to rule it out.

It's worth sitting with how ordinary the bug looks in isolation. There's no off-by-one, no race condition, no missing null check. The function did exactly what its author wrote: iterate a list, return whether anything unresolved turned up. The defect is one level up, in the assumption that an empty result and a clean result look the same to the caller. They don't, and nothing in the code enforced that they shouldn't be conflated. This is the shape every "default: assume safe" branch takes. Somebody writes a taxonomy with a state that means "we checked and it's fine," wires a fallthrough for the case where nothing else matched, and the fallthrough gets reached whenever the checking step itself didn't run. The taxonomy still looks complete. Every branch still returns something. The thing that's missing is a distinction between two different kinds of nothing: nothing wrong, and nothing looked at.

If you're building a fault or outcome taxonomy anywhere, this is the question worth asking of every terminal state that claims to mean "we proved X didn't happen": does reaching this state require having examined anything, or does it just require nothing else having triggered first? An enum branch reached by elimination, not by evidence, will eventually get reached by a case that never got evidence-gathering the chance to run. It will pass every test you write for the cases where verification did run, because those all produce a populated, resolved list. The gap only shows up on the input nobody thought to write a test for: verification that never started.

Flow's own codebase has a working version of the alternative right next to this bug. [PR #264](https://github.com/OpenAdaptAI/openadapt-flow/pull/264), the verifier adapter platform, defines explicit adapter results including `CONFIRMED`, `REFUTED`, `UNAVAILABLE`, `STALE`, `CONFLICTING`, and `INDETERMINATE`, and maps them to the transaction outcome taxonomy "without a silent-success path," in the PR's own words. `UNAVAILABLE` and `INDETERMINATE` exist precisely so that "couldn't check" has somewhere to go that isn't the same place as "checked and it's clean." That's the structural fix #280 applies one level up: `classify_transaction_outcome()` now has to require positive evidence of absence before it's allowed to reach `HALTED_BEFORE_EFFECT`, per the PR's own title. Not fewer branches. A branch that can only be reached by something having actually looked.

The general version of that rule doesn't need any of Flow's specifics to be useful. Take any enum in your own system where one member is supposed to mean "we ruled this out." Trace, by hand, every code path that produces that member. For each one, ask whether it required inspecting real evidence or whether it's just what's left over once the other branches didn't fire. If it's the second kind, you have a branch that will one day report "confirmed clean" about a state nobody ever looked at, and it will do so with exactly the same confidence as the branches that did the work.
